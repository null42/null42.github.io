# Firefly Mod 迁移目标拆分设计

日期：2026-07-24
状态：用户已批准并作为当前执行目标生效
适用分支：`codex/firefly-mod-knowledge-migration`

## 1. 背景

原迁移目标经过多轮追加，已经同时覆盖内容迁移、视觉复刻、本地播放器、功能页、加密 Markdown、发布流程和未来私密阅读器。不同子系统共享一个无限增长的完成门，导致恢复成本、重复验证和审查范围持续增加。

本设计将工作拆分为两个顺序目标。当前工作树和既有迁移规格全部保留，不重置、不重做已通过阶段。

## 2. 目标结构

### 2.1 目标 1：Firefly Mod 博客迁移与正式发布

目标 1 采用“尽快发布”边界，持续执行到正式站部署和线上验证完成。

#### 包含范围

1. 闭合当前 Loader 与 V2.2.2 首页滚动叙事的规格审查和代码质量审查。
2. 实现真实本地播放器和共享持久音频状态的全局迷你播放器。
3. 只展示已经真实实现、通过测试且当前启用的功能。未实现、未启用或依赖缺失后端的相册、日历、友链、留言、赞助、AI 等入口和页面壳全部不展示。
4. 修复加密 Markdown，使本地解密后的内容与普通文章共享 Markdown 渲染和增强能力，包括标题、代码、KaTeX、Mermaid、PlantUML、图片和链接。
5. 保持 `content/` 为唯一规范内容源，保持 `sectionId → routeId → stageId → articleId` 四级模型。
6. 完成 URL、Pagefind、Sitemap、附件、公开性矩阵和 generated output 泄漏回归。
7. 完成生产构建、Astro Check、自动化测试、生产 E2E、Lighthouse、安全扫描和视觉基准对比。
8. 自动创建迁移提交、fetch 并推送迁移分支，核对同 SHA CI artifact。
9. 在阶段 8 展示同 SHA 生产预览和验收截图，等待用户人工批准。
10. 只有用户明确批准后，才能执行回滚演练、更新 `main`、等待 GitHub Pages 并完成线上回归和最终报告。

#### 明确排除

- 不实现 Cloudflare Worker、KV、Vectorize、Workers AI 或 RAG。
- 不实现动态留言后端、云端账户、云端阅读进度或多设备同步。
- 不真实实现当前缺少安全后端的 AI、赞助提交等操作。
- 不创建或展示“功能暂未开放”静态壳；功能完成并通过质量门前不得出现在首页、导航或公开路由入口。
- 不在目标 1 中实现 TXT/EPUB 私密阅读系统。
- 不复制参考作者的账号、二维码、联系方式或其他个人身份配置。

#### 完成标准

- 所有目标 1 规格审查和代码质量审查达到 `Critical = 0`、`Important = 0`。
- 内容、附件、URL、导航覆盖和公开性矩阵验证通过。
- 加密 Markdown 的功能与安全边界通过生产 E2E。
- 桌面、平板和移动端视觉符合 V2.2.2 主参考方向，并有参考对比证据；不得混入与站点内容无关的角色或模型图片。
- 真实本地播放器不依赖外网，Swup 往返后保持单实例并可释放。
- 同 SHA 分支 CI、artifact、生产预览和回滚证据齐全。
- 用户批准后正式部署成功，线上回归通过并生成最终迁移报告。

### 2.2 目标 2：私密 TXT/EPUB 阅读系统

目标 2 只能在目标 1 正式发布并完成线上验收后启动，并使用独立规格、计划和质量门。

#### 核心范围

- 提供低可发现性的入口，但不把“入口隐蔽”视为安全机制。
- 阅读内容必须加密后部署，密钥不得进入仓库、日志、CI artifact 或生成产物。
- 只在浏览器本地解密。
- 支持超大 TXT 文件的分段读取、虚拟化渲染、编码识别、搜索和阅读进度。
- 支持 EPUB 章节、目录、内部链接、图片、主题、字体、书签和阅读进度。
- 使用用户指定的本地 TXT 与 EPUB 目录做压力测试；绝对路径只通过未提交的本机配置提供，不写入仓库文件、日志或构建产物。
- 测试书籍、文件内容、路径清单和解密数据不得提交或泄漏到生产构建。

#### 安全原则

- 未持有解密密钥的访问者即使知道 URL，也不能得到正文。
- 静态页面中的路由隐藏、特殊点击序列或秘密快捷键只能降低可发现性，不能代替加密和密钥验证。
- private、hidden、encrypted 的现有公开性矩阵继续生效，并在目标 2 设计中扩展文件级公开性规则。

## 3. Git 与发布边界

- 允许在迁移分支自动暂存、提交、fetch 和正常推送。
- 首次推送前必须核对同名远端分支和 tracking 状态。
- 禁止 force push。
- 阶段 8 人工批准前禁止合并或更新 `main`。
- 用户批准只对展示过的同 SHA 生产预览生效；SHA 变化后必须重新验证和重新批准。

## 5. 执行顺序

1. 恢复并闭合当前目标 1 的 Task 7。
2. 完成 Task 8 真实本地播放器，跳过旧 Task 9 静态功能壳，再完成 Task 10–12。
3. 自动提交并推送迁移分支，完成 CI 和同 SHA artifact 验证。
4. 在阶段 8 等待用户人工批准。
5. 批准后完成回滚演练、`main` 更新、Pages 部署和线上回归。
6. 目标 1 完成后，创建目标 2 的独立设计规格和实施计划。
